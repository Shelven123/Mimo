# Recharge foundation — purchases remain disabled

Implemented: Recharge information/history page connected from Me and Wallet; server-owned active-package catalog; exact price/diamond strings; paginated own-user recorded orders; safe rendering and account cleanup. Purchase buttons always disabled in this release. No provider checkout or browser order submission is wired in the page.

Database order creation takes only package UUID and retry UUID, derives owner from Auth and snapshots the configured price/diamonds/currency/provider. Reusing a key returns its original order, including after a price/activation change; changing the package for that key rejects. Direct client recharge INSERT and financial-state mutations are denied, closing the inherited fake-paid-row path. Historical rows are not rewritten or validated retroactively.

Internal accounting API: ONLY service_role may execute confirmation. It assumes a trusted backend has already authenticated the external provider event/signature and mapped it to the correct order. This release DOES NOT implement that provider verification. The function verifies snapshot amount/currency/provider, locks order and wallet, stores a unique provider/reference receipt, credits exact bigint diamonds, writes ledger and marks paid atomically. A repeated matching paid receipt returns false with no extra credit. Mismatches, another order's receipt, legacy/terminal orders, missing wallet, overflow and ledger failure reject/roll back. Legacy recorded paid references also cannot be reused. Receipt store is private, no direct client grants and explicit deny-all client RLS. Public wrappers are SECURITY INVOKER; privileged helpers are private with empty search_path and narrow EXECUTE grants.

Verified: 107 automatic checks including isolated PostgreSQL create/retry/price snapshot/ownership/forgery/service privilege/duplicate receipt/mismatch/atomic failure/rollback and safe DOM/account cleanup. Syntax/whitespace pass. Production migrations applied; permissions/RLS confirmed; active package count is zero and no-UID history returns zero rows. No real user wallet/ledger/order rows were changed by this deployment. Advisors' inherited warnings are recorded in NOTIFICATION_CENTER_REVIEW.md; the new private no-policy informational finding was addressed with explicit restrictive deny-all policy.

Not Verified: production transactional settlement, real provider checkout/webhook signature handling, refund reconciliation, callback concurrency on production, phone recharge UI and end-to-end real payments. PGlite serialized tests do not prove production concurrency. No package prices, provider account, Host split or payout rate is approved by the user's generic continue/confirm messages. Fixture prices are test-only, never seeded to production.

Activation prerequisites: approve packages and provider; configure merchant secrets securely in backend; build checkout with server-owned prices and provider idempotency; verify callbacks with provider signature, event/order mapping and paid status; only then call the service-only accounting API. Handle late payment after cancellation, failed events and refunds explicitly. No backend/Edge Function currently performs these operations. Enabling a package alone DOES NOT enable checkout or make purchase buttons work. Payment/settlement secrets must never enter frontend files.

Rollback: revert frontend and apply database/rollback-recharge-foundation.sql. The rollback disables APIs while preserving financial evidence and client forgery protections; it does not reverse paid balances, delete receipt records or restore insecure INSERT grants. The explicit receipt RLS remains in place.

Source consulted: [Supabase Database Functions](https://supabase.com/docs/guides/database/functions), including invoker/definer/search_path/EXECUTE controls. See PAYMENT_READINESS.md for the owner inputs still needed.
